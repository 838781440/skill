# Pressure Test（万物压力测试）

对**任何东西**进行系统化的压力测试——技术方案、商业模式、市场策略、产品想法、人生决策、职业规划。**用实际数据而非直觉说话，用逻辑而非立场找漏洞，禁止凭经验给结论。**

> v2.0 核心升级：从"技术方案压力测试"升级为"万物压力测试"。所有被测对象统一用 **数据维度** + **逻辑维度** 双重验证。

---

## 触发方式

| 你说 | 触发模式 |
|:----|:--------|
| **压力测试 XX** | 标准模式：多维度实测 + 逻辑推敲，5-15 分钟 |
| **快速压力测试 XX** | 紧凑模式：只测 3 个最关键维度，3 分钟内出结论 |
| **给 XX 挑刺 / 找短板** | 同上 |
| **验证 XX 靠不靠谱** | 同上 |
| **对拍 XX 和 YY** | A/B 对比，同一条件比差异 |
| **穿透 XX** | 深度模式：把所有隐藏假设挖出来，不留死角 |

无论被测对象是代码、方案、想法还是决策，触发方式一致。

## 工作流程

### Phase 0: 基线 + 成本评估

**正式测试前先看清楚代价：**

- **如果涉及工具调用**（查数据/跑代码），先确认资源够用（内存 <500MB 禁止开浏览器）
- **如果是纯想法分析**（不调外部工具），不需要资源检查，但要在报告里标注「纯逻辑分析，未经数据验证」
- **成本分类：**
  - 🔧 **工具密集型** → 限 3 次工具调用/维度，优先免费渠道
  - 🧠 **逻辑密集型** → 无限次逻辑推演，但不伪造数据
  - 🔄 **混合型** → 先逻辑找关键假设，然后用数据验证最关键的那 1-2 个

### Phase 1: 拆解被测对象

不区分技术/非技术，统一拆解为三层：

**表层：** 被测对象的核心主张是什么？
> 例：技术方案→核心实现路径 | 商业想法→核心价值主张 | 职业选择→核心决策逻辑

**中间层：** 它依赖哪些条件成立？
> 例：技术方案→依赖库稳定/API 可用 | 商业模式→客户愿意付这个价 | 职业选择→该行业有上升空间

**底层：** 哪些关键假设不能验证就是赌博？
> 例：技术方案→并发量判断 | 商业模式→获客成本假设 | 职业选择→收入预期

### Phase 1.5: 策略选择

根据**被测对象类型**自动匹配测试维度优先级：

| 被测类型 | 核心风险 | 优先级（高→低） |
|:--------|:--------|:--------------|
| 🔧 **技术/工程方案** | 实现不可靠、性能瓶颈、边界遗漏 | 异常 > 边界 > 数据验证 > 性能 > 容量 |
| 💼 **商业模式/创业想法** | 假设不成立、市场不买单、算不过账 | 逻辑推敲 > 竞品对拍 > 数据验证 > 财务建模 > 规模风险 |
| 🧭 **职业/人生决策** | 认知偏差、信息盲区、沉没成本 | 逻辑推敲 > 数据验证 > 反向思考 > 时间轴推演 > 情感审视 |
| 📢 **市场/营销策略** | 目标错位、渠道无效、ROI 假象 | 数据验证 > 竞品对拍 > 逻辑推敲 > 边界极端化 |
| 🏠 **购买/投资决策** | 信息不对称、隐藏成本、流动性 | 财务建模 > 数据验证 > 逻辑推敲 > 场景极端化 |
| 🎯 **产品方向/功能** | 需求假象、使用率不如预期 | 数据验证 > 竞品对拍 > 逻辑推敲 > 边界极端化 |
| 📝 **写作/内容方案** | 受众偏差、说服力不足、事实错误 | 逻辑推敲 > 数据验证 > 情感审视 > 反向阅读 |
| 🔮 **预测/判断** | 确认偏误、幸存者偏差、样本偏差 | 反向思考 > 逻辑推敲 > 时间轴推演 > 数据验证 |

> 默认覆盖所有维度。快速模式只按优先级选前 3 项。

### Phase 2: 多角度测试

每个被测对象都从两个轴交叉分析：

#### 🔬 数据维度（能用工具就拿数据，不能就明说）

| 维度 | 技术方案 | 商业/想法 | 职业/决策 |
|:----|:--------|:----------|:---------|
| 🎯 **现实验证** | 跑一个最小用例 | 查竞品/市场规模 | 查行业薪酬/岗位数 |
| 🚫 **异常场景** | 依赖挂/输入异常 | 客户不买/对手打价格战 | 最坏情况能扛多久 |
| 🔁 **边界条件** | 空/大/并发 | 最低/最高定价 | 最小/最大收入预期 |
| 📦 **容量/规模** | 批量处理能力 | 规模化后成本结构 | 可持续性（5年/10年） |
| ⏱ **效率/时间** | 每步耗时 | 多久能盈亏平衡 | 时间投入 vs 回报周期 |
| 💰 **成本/财务** | 服务器/API 费用 | 启动成本+运营成本 | 机会成本+沉没成本 |

#### 🧠 逻辑维度（所有类型通用，不依赖工具）

| 维度 | 核心问题 | 典型陷阱 |
|:----|:--------|:--------|
| 🔎 **假设检验** | 哪些关键假设还没被验证？ | 把假设当事实 |
| 🔄 **反向思考** | 如果目标是失败，怎么做最有效？ | 只往好的方向想 |
| 📊 **幸存者偏差** | 是不是只看成功案例忽略了失败？ | 幸存者偏差 |
| 🎲 **默认选项** | 什么都不做/维持现状会怎样？ | 行动偏见 |
| 🔮 **时间推演** | 1周/1月/1年/5年后的推演 | 短期思维 |
| 🎭 **反向扮演** | 如果你是竞争对手会怎么干掉它？ | 站位单一 |
| 🧩 **隐藏依赖** | 方案依赖于哪些不受控的条件？ | 链条断层 |
| 📐 **第二层思考** | 所有人都知道这个，然后呢？ | 从众思维 |
| 💸 **第二层成本** | 除了明面上的，还有什么隐性成本？ | 只看直接成本 |
| 🔗 **因果正确性** | A 真的导致了 B 吗？还是相关关系？ | 因果混淆 |
| 🧮 **数学正确性** | 这个数字算得对吗？增长率可持续吗？ | 计算错误/无根据增长 |
| 🔬 **替代解释** | 还有别的解释能产生同样的现象吗？ | 唯一因谬误 |
| 💭 **情感审视** | 这中间有没有情绪驱动的判断？ | 恐惧/贪婪/焦虑/ego |

### Phase 3: 记录测试结果

**工具调用测试**（如果有）→ 按以下格式：

```
测试项：XXX
方式：web_extract / web_search / browser / terminal
实际结果：成功/失败, 耗时 Xs, 内容 XX
与预期差异：有/无
```

**逻辑推演测试**（所有类型）→ 按以下格式：

```
假设：XXX
逻辑链：因为 A → 所以 B → 隐含 C
漏洞：A 可能不成立因为 YY
验证建议：用 XX 方法可验证
```

### Phase 4: 问题分类

统一结果分类，不论被测对象类型：

| 标记 | 含义 | 严重度 |
|:---|:----|:------|
| 🔴 **致命** | 核心假设立不住，方案不可行 | 必须重新考虑 |
| 🟡 **高风险** | 有 1-2 个关键漏洞需加固 | 必须解决 |
| 🟢 **可优化** | 不影响可行性但可以更好 | 建议处理 |
| ⚪ **不确定** | 缺乏数据判断，需要进一步验证 | 建议收集数据 |
| 💡 **洞察** | 压力测试过程中发现的意外发现 | 额外价值 |

### Phase 4.5: 行动清单

压力测试不能只发现问题不给出路。每个问题必须有对应的**行动项**：

| 问题 | 行动 | 优先级 | 预计耗时 | 谁来干 |
|:----|:----|:-----:|:--------|:------|
| 🔴 致命问题描述 | xxx | **P0 立即** | 2h-1天 | 负责人 |
| 🟡 高风险描述 | xxx | **P1 本周** | 1-3天 | 负责人 |
| 🟢 建议优化描述 | xxx | **P2 本月** | 1-5天 | 负责人 |
| ⚪ 待验证描述 | xxx | **P3 持续** | - | 负责人 |

**优先级定义：**
| 标记 | 含义 | 处理时限 |
|:---|:----|:--------|
| **P0 🔥** | 必须马上解决，不解决就崩 | 24小时内 |
| **P1 ⚡** | 本周内必须处理 | 7天 |
| **P2 📅** | 本月内规划 | 30天 |
| **P3 🔭** | 持续观察/备选方案 | 持续 |

> 行动清单必须包含"预计耗时"——没有时间估计的行动项等于没提。即使估算不准，也要给出范围（如"2h-1天"）。

### Phase 5: 收尾检视

压力测试完成前，必须做一次**收尾检视**，确认没有遗漏：

1. **盲点自查**：这次测试有没有忽略的维度？
   - 技术方案：有没有漏掉安全/性能/异常？
   - 商业想法：有没有漏掉竞品/政策/现金流？
   - 人生决策：有没有漏掉情感/家人/长期影响？

2. **证据复审**：所有结论中，有多大比例是有数据支撑的（🔵🔵）vs 凭经验推断的（🔴）？
   - 如果超过50%是🔴，必须在报告中声明「可靠性有限」

3. **一句话总结**：用一句话概括这次压力测试的核心结论。
   - 格式：**「被测对象在 XX 方面存在 XX 风险，建议优先解决 XX，整体评级 XX/10」**

4. **后续建议**：如果需要进一步深入，建议做什么？
   - "建议用调度师做深度分析"
   - "建议用 grill-me 做逐项追问"
   - "建议收集 XX 数据后再测一次"

所有类型统一报告结构：

```
## 压力测试报告：[题目]

### 被测对象
一句话描述被测的是什么

### 测试方式
- 类型：工具测试 / 逻辑推演 / 混合
- 涉及工具/逻辑维度：[列表]
- 数据来源：[如果有的话，注明来源]

### 核心假设清单
| 假设 | 验证状态 | 风险等级 |
|:----|:--------:|:-------:|

### 测试结论

#### 🔴 致命问题
问题：[描述]（严重度）
- 发现方式：XXX
- 影响：XXX
- 建议：XXX

#### 🟡 高风险项
同上

#### 🟢 优化建议
同上

#### ⚪ 待验证
同上

### 整体评估
| 维度 | 评分 | 说明 |
|:----|:---:|:----|

### 特别提示
- 如果是纯逻辑分析，标注「⚠️ 纯逻辑分析，建议用数据验证关键假设」
- 如果有工具验证过，标注「✅ 关键假设已有数据支撑」

## 使用限制

- **纯逻辑分析不造数据。** 逻辑推演只能告诉你「有问题」，不能告诉你「答案是什么」。需要数据来验证的，标注出来让用户自己去查或授权你查。
- **不存 gbrain。** 压力测试是临时分析，内容不过度到知识库。
- **无法替代专业咨询。** 商业模式压力测试可以提供早期检视，但不能保证所有风险都被发现。
- **子任务约束：** 使用 `delegate_task` 时必须在 context 中要求「不存 gbrain」。

## 经验教训（持续积累）

- 技术类：浏览器开销不能靠估算（实测 1,162 MB/14 进程）
- 商业类：最常见的错误是把市场规模当自己的份额
- 决策类：确认偏误是最隐蔽的敌人——你更相信支持自己观点的证据
- 数据类：「感觉还行」不够，要量化（`content.length > 200 chars` 之类的硬标准）
- 通用：成功的定义要具体——「这个想法不错」不如「6 个月内能盈利」
