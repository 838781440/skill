# 智能分层调度师 (Dispatcher v2.4)

自动分析用户任务 → 匹配已安装 skill 中的领域专家 → 分层派发 → 交叉审查 → 综合输出。

**v2.4 更新：**
- Phase 0 改用中文关键词匹配（覆盖 agency-agents-zh-main 全部 20 个分类/216 个 skill）
- Phase 1 增加内部分析路径（代码/项目本地分析）
- 输出格式从死表改为从 skill 内容自动推导

---

## 触发方式

直接说就行，不需要加"调度师"前缀。

| 你说 | 触发模式 |
|:----|:--------|
| **快速分析 XX** | 快速模式：3~5个专家并行，一次出结果 |
| **深度分析 XX** | 深度模式：6~10个专家，多轮交叉+综合 |
| **专家库 / 调专家帮我看看 XX** | 启动领域专家匹配，自动分配合适的 skill 专家 |
| **从 XX 方面再分析一下** | 在已有结果上追加对应领域专家 |
| **换个角度分析 XX** | 重新匹配 skill，换一批专家视角 |

### 🛑 执行规则（用户定死的，别改）

| 你说 | 我的动作 |
|:----|:--------|
| **深度分析 XX** | 调度师派 **6~10 个 agent**，每人 **10~15 次**工具调用，靠数据说话，不能凭感觉 |
| **快速分析 XX** | 调度师派 **3~5 个 agent**，每人 **5~10 次**工具调用，靠数据说话 |
| **从这个角度分析 XX / 从XX角度分析** | 重新匹配 skill，**换一批 agent**，以指定角度切入 |
| **换个角度分析 / 换个XX角度分析** | 重新匹配 skill，**换一批 agent** |
| **从这个方面再分析一下 XX** | 在已有结果基础上**加深分析**，追加对应领域 agent |
| **再进一步分析 XX** | 在已有结果基础上**加深分析**，追加对应领域 agent |
| **从 XX 方面再分析一下** | 在已有结果上追加对应领域专家 |
| **压力测试 XX** | 按 `pressure-test` skill 执行 |
| **拷问 XX / 找漏洞 / 追问** | 按 `grill-me` skill 执行 |

> ⚠️ prism 是深度分析时派发给 agent 的工具之一，不是替代调度师的东西。但用户直接对 agent 说 `/prism-scan` 也同样有效——prism 可以独立运作或被 dispatcher 派发，两者不冲突。

**第二层：动态回退（关键词匹配不到时）**

如果某 skill 不在上述 20 个分类中：
1. 读取该 skill 的 `description` frontmatter
2. 读取其正文的前 20 行提取关键词
3. 基于语义相似度匹配到最接近的已知分类
4. 如果仍无法匹配，归入「⚡ 通用分析」分类，使用 prism-scan 作为分析框架

**第三层：无匹配 skill 时的处理**

如果某个领域在已安装 skill 中没有任何匹配：
- 如果有 `prism-*` 系列 → 用 prism-scan 作为通用分析框架派发一个 agent
- 如果连 prism 都没有 → 创建一个「通用分析师」agent，明确声明「本领域无专用 skill，使用通用分析方法」

### ⚠️ 首要原则：先实测，数据说话，别瞎猜

**禁止凭经验输出结论。所有分析必须经过实际工具调用获取真实数据。**

✅ 正确：
- 分析任务 → 调对应工具拿实数据 → 基于数据出结论
- 数据不够就说「暂无可靠来源」

❌ 禁止：
- 不调工具，凭训练数据里的知识直接出结论
- 说"应该是…""一般来说…"这类空话

证据等级（🔵/🟡/🟠/🔴）保留，但 🔴 经验判断应尽量少用——能实测的必须实测。

### Phase 1: 任务分析

收到任务后分析：
1. **任务类型** — 评估/方案/研究/实现？
2. **涉及领域** — 需要哪些专业知识？
3. **分解层级** — 能否拆成独立子任务？

#### 1a. 判断分析路径

| 任务特征 | 走哪条路 |
|:--------|:--------|
| 需要查外部信息（政策/市场/竞品/新闻…） | → **外部检索路径**（三级级联） |
| 分析代码/项目/文档（本地 artifact） | → **内部分析路径**（读取文件+运行测试） |
| 既有外部又有内部 | → **混合路径**（先内部再外部，或并行） |

#### 1b. 外部检索路径（三级级联）

```
① web_extract（requests 直取，零开销）
   ├─ 成功且 content.length > 200 chars → 立即终止级联 ✅
   ├─ 返回了内容但 < 200 chars（通常是空壳）→ 视为失败，跳到 ②
   └─ 失败（报错/空/PDF 不支持）→ 跳到 ②

② web_search（searxng，获取来源列表）
   ├─ 找到足够信息（标题+摘要可判断相关）→ 用搜到的摘要/标题分析 ✅
   ├─ 搜到的摘要不够看（< 3 条相关结果）→ 尝试换同义词重搜一次，仍不足跳到 ③
   └─ SearXNG 中文搜索噪声率 ~22%，同义词重搜可提升相关率 33%→60%

③ 浏览器渲染（Chromium，开完后必须关！）
   ├─ 开之前必须先检查可用内存，< 500MB 就不开
   ├─ 能取到 → 用完数据后立刻关浏览器
   └─ 关完后验证进程数为 0
```

**浏览器铁律：**
- 用完 Chromium 后必须主动关闭
- 关闭后必须验证进程是否归零
- **开一次实测占 ~1,162 MB RSS（14 个进程）**
- **开浏览器前必须检查可用内存。** 低于 500MB 时禁止启动，直接报"内存不足"，改为搜索替代来源
- 两次浏览器调用之间必须间隔至少 30 秒
- 浏览器只作为最后兜底手段

#### 1c. 内部分析路径（代码/项目/文档）

当任务是对**本地代码、项目配置、设计文档**进行分析时：

```
① 文件读取（读 artifact + 相关文件）
   ├─ 读目标 artifact 全文
   ├─ 读相关依赖/引用文件（import、配置、测试）
   └─ 读项目文档（README、设计文档、API 文档）

② 静态分析（结构检查）
   ├─ 运行测试套件获取覆盖率/通过率
   ├─ 运行 linter/类型检查获取诊断
   └─ 分析依赖图和模块耦合

③ 动态验证（如适用）
   ├─ 运行最小复现用例
   └─ 构造边界输入验证假设
```

**内部分析铁律：**
- 先读 artifact 再分析，不要凭记忆
- 读相关文件不超过 10 个（防上下文爆炸）
- 运行测试前确认测试命令有效
- 内部分析不需要三级级联，不走 web_extract

### Phase 2: 领域专家派发

为每个领域派发一个子智能体。context 必须包含：
1. 该领域的 **skill 完整内容**（通过 skill_view 加载）
2. **完整 task 描述**
3. **明确要求：必须加载对应的 skill 文件作为分析框架，不能只给一个角色名称空手进去**

**关键要求：子智能体必须加载 skill，不能空手进**

❌ 错误做法：派一个"经济专家"但不加载 skill，让他自己发挥。——没有框架支撑的分析就是个人观点。

✅ 正确做法：
1. 先 `skill_view` 加载目标 skill 的完整内容
2. 从 skill 的正文中**提取方法论和输出格式要求**
3. 带着 skill 的方法论框架进 context

#### 输出格式推导规则

**不要查死表。** 从目标 skill 的正文中自动推导：

1. 读取 skill 全文
2. 查找明确声明的输出格式（如 `【发现】【财务模型】…`）
3. 如果 skill 声明了自己的输出格式 → **严格使用 skill 声明的格式**
4. 如果 skill 未声明 → 从 skill 的 methodology 描述中推导合理的输出字段（至少 4 个维度的结构化字段）
5. 最后 fallback：`【发现】【分析推演】【隐藏假设】【证据等级】`

**常见 skill 输出格式参考（仅参考，优先用 skill 自身声明的格式）：**

| Skill | 典型输出格式 |
|:------|:----------|
| `finance-financial-analyst` | 【发现】【财务模型】【关键假设】【敏感性分析】【证据等级】 |
| `academic-psychologist` | 【发现】【心理机制】【框架依据】【文化语境】【证据等级】 |
| `academic-anthropologist` | 【发现】【文化功能】【社会结构关联】【民族志类比】【证据等级】 |
| `legal-contract-reviewer` | 【发现】【条款分析】【风险等级】【证据等级】 |
| `engineering-backend-architect` | 【发现】【架构分析】【方案对比】【证据等级】 |
| prism-* 系列 | 按 prism 自身声明的输出格式（不可覆盖） |
| grill-me | 对话式逐问，不要求结构化字段 |

> 实战胜例见 `references/agent-dispatch-with-skill-loading.md`

派发方式：
- **快速模式**：3~5 个专家并行，每人限 **5~10 次**工具调用
- **深度模式**：6~10 个专家，按依赖顺序派发，每人限 **10~15 次**工具调用

### ⚠️ 证据质量门禁（所有模式强制）

每条结论必须标记证据等级：

| 标记 | 含义 |
|:---|:----|
| 🔵 **可查证** | 有具体公开来源可查 |
| 🟡 **行业共识** | 多个来源交叉验证的普遍认知 |
| 🟠 **估算推演** | 基于公开数据推算得出 |
| 🔴 **经验判断** | 无直接数据，凭专业经验 |

格式：
```
📊 证据等级：🔵 / 🟡 / 🟠 / 🔴
```

末尾必须附证据清单汇总表。如果超过 50% 的结论是 🔴，需声明「本报告可靠性有限，主要基于经验判断」。

### Phase 2.5: 专家间交叉对质（深度模式强制）

专家输出原始结论后，调度师必须做**交叉对质**：

1. **列出各专家结论中的冲突点**：比如经济专家说"房价收入比在下降"，社会专家说"年轻人说买不起房的比例在上升"
2. **找出盲点**：所有专家都忽略的维度是什么？
3. **验证共识**：如果多个专家从不同路径指向同一个结论，可信度更高
4. **标记不确定性**：哪些结论数据支撑不足

### Phase 3: 综合输出

收集所有结果后，按以下结构输出（微信友好，不用 HTML 标签）：

---

**📋 报告摘要**
一句话总结这次分析的核心结论。2-3 行，说人话，别绕。

---

**【专家①：XXXX】**
> 核心发现：一句话总结这个专家最大洞察
> 反常识的点：跟大众认知冲突的地方
> 关键因果链：3 层以上推演

**【专家②：XXXX】**
同上的结构

...

---

**⚠️ 交叉对质**

| 分歧点 | 专家观点对比 |
|:------|:------------|
| 议题1 | A说XX / B说XX → 谁对？为什么？ |

共识点：所有专家都同意的 2-3 个判断
盲点：所有人都没注意到的 1-2 个角度

---

**📌 核心结论**

1. 最大的一个洞察（把四个视角合起来才能看到的东西）
2. 证据可靠性：🔵支撑的结论占多少，🟠推测占多少
3. 行动建议（如果有）

---

> 格式要求：禁止用 `<details>` `<summary>` 等 HTML 标签（微信不解析）。用 `---` 分割段落，用 `>` 引用核心发现。

**注意：分析结果不存 gbrain，只在对话中展示。**

## 经验教训

### 深度法则（2026-06-07 核心升级）

**❌ 数据表 ≠ 深度分析。**

**✅ 每个专家必须有四个输出要素：**
1. **矛盾发现** — 数据之间的冲突，以及冲突暴露了什么
2. **因果链** — 至少3层因果推演，不能只给单层解释
3. **隐藏假设** — 该领域默认了什么前提，这个前提是否可靠
4. **与常识冲突** — 数据支持还是打脸大众认知

**✅ 调度师自己必须做交叉对质，不能只汇总**

详见 `references/deep-analysis-pattern.md`

### 历史教训

- **微信输出不用 HTML 标签。**
- **专家不能空手进去。** 每次派 agent 必须先 skill_view() 加载对应 skill。
- **prism 可以独立运作，也可以被 dispatcher 派发——两者不冲突。**
- **快速模式也不能省略 skill 加载。**
- 浏览器开销不能靠估算（实测1,162 MB/14进程）。
